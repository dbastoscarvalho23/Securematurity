# AGENTS.md — Securematurity / AnkoraOne

## App overview
Base44 app (Vite + React 18 frontend) that connects to the Base44 cloud backend.
- GitHub repo: `dbastoscarvalho23/Securematurity`
- Internal app name (in `base44/config.jsonc`): `AnkoraOne`
- Backend URL is provided via `VITE_BASE44_APP_BASE_URL` (proxied by the base44 vite-plugin under `/api`).

## Running the app (sandbox)
```
docker compose -f docker-compose.base44.yml up -d
```
- Node 22 slim image, repo bind-mounted at `/app`; `.base44/dev-entrypoint.sh` installs the Base44 CLI + Deno (dev-only tooling, never added to `package.json`), runs `npm install`, writes the gitignored `base44/.app.jsonc` link pointer from `VITE_BASE44_APP_ID`, then runs `base44 dev`.
- `base44 dev` serves **this branch's backend locally**: functions run in Deno, entities in a local in-memory database, and it spawns vite (port 5173, mapped to host 3000) with `/api` proxied to `http://localhost:4400`. Branch entities/functions therefore work without merging to `main`. Verified: `Workspace` answers 200 locally where the deployed backend returns 404.
- Auth: `base44 login` (device code) is already done; the token lives in the `base44-cli-auth` volume mounted at `/root/.base44`. To re-auth, run `docker compose -f docker-compose.base44.yml exec web base44 login`.
- **Local data is in-memory and is wiped on every container restart** (and whenever an entity schema changes). Re-seed via the `seedLicenseData` / `migrateExistingWorkspaces` functions and any test records.
- Local dev seeds exactly one user: the CLI account (`victor.pereira@dcabconsulting.com`), stored as `role: "admin"`. **Roles are now migrated to the canonical spelling.** The entity RLS matches `user_condition` by **exact string** and the backend applies **no** normalisation (verified in the CLI bundle: `evaluateUserCondition` → `getRLSFieldValue` → `userValue !== expected`), so the canonical spelling has to be *stored*, not just resolved. `logUserLogin` rewrites the stored role to `normalizeRole(role)` on every login (`admin` → `master_admin`, `user` → `employee`, `partner_admin` → `workspace_admin`) and audits the change; `adminUpdateUser` normalises the role it persists; every entity RLS — isolation, operational **and** the catalogue/tenant ones (Comment, Training, Notification, licensing, KnowledgeArticle, …) — names the canonical roles; and the frontend no longer compares role literals, going through `src/lib/rbac.js` (`isPlatformOwner` / `hasRole` / `normalizeRole`). The legacy spellings stay in the `User`/`InvitedUser` role enums so un-migrated records still validate. **Local caveat:** the in-memory backend silently ignores writes to `User.role` (verified: `asServiceRole.entities.User.update(id, { role: "master_admin", language: "pt" })` persists `language` and drops `role`), so the local account stays `admin` and the canonical RLS does not match it — which is why the platform admin still sees an empty Customers list and an empty AuditLog **locally only**. On a real backend the account flips to `master_admin` on the first login. Any password works locally. `User` create/delete are ignored locally, so extra users cannot be created.
- Local backend quirks: a field that backend code clears with `null` (e.g. `Assessment.overall_score` when an assessment is reopened) must be declared with a union type such as `["number", "null"]` — the validator rejects `null` on a single-type field ("Input should be a valid number"), and entity updates are partial so omitting the key never clears it; unknown keys are silently dropped by `filterFields`, so code keys must match schema names exactly (e.g. `result_history[].completed_date`, not `completed_at`) — the same rule applies to nested snapshot objects, which is why `result_history[].methodology` declares `framework_versions` and `questions`; `Workspace.parent_id` is `["string", "null"]` for the same reason (root workspaces are created with `parent_id: null`, which a single-type field rejects); the SDK realtime websocket logs `connect_error` / `timeout` (REST and functions are unaffected).
- **No outbound network from backend functions (do not call `fetch` on an app path).** A function that `fetch`es an external host fails the TLS handshake here — the sandbox proxies egress with a certificate workerd does not trust — and the runtime prints `workerd/jsg/util.c++ ... kj/compat/tls.c++: failed: TLS peer's certificate is not trusted` plus a long `workerd@…` stack, once per call. The JS `try/catch` still receives the rejection, so the function returns normally, but the log reads like a crash (this is what filled the log during the legal-repository work). `seedLegalRepository` used to contact every official link on each run; it now records new versions as **unverified** and only checks links when the caller explicitly asks (`{ check_links: true }`), leaving confirmation to the `verify` action of `manageLegalRepository` (the UI verifies with `method: "manual"`). `storeFileToCloud` is the only other caller and only when a cloud-storage provider is configured.
- **Array-based RLS is only half-emulated locally:** the in-memory backend honours the `delegated_view_customer_ids` branch of the read rules, but a tenant present only in `delegated_edit_customer_ids` is hidden on read and refused with `403 Permission denied` on write, even though every operational entity declares both branches. Treat this as a local emulator limitation, not a repository defect — delegated-editor access has to be verified against a real backend.
- Secrets (`VITE_BASE44_APP_ID`, `VITE_BASE44_APP_BASE_URL`) are delivered via `/run/base44/app.env`.
- Vite `server.host: true` + `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` env var handle the preview proxy hostname.

## Structure
- `src/pages/` — 45 page components, all routed in `App.jsx` (some routes are redirects).
- `src/components/` — 133 app components + 49 shadcn/ui primitives.
- `base44/entities/` — 48 entity definitions (JSONC), including Workspace, UserCustomerAssignment, KnowledgeArticle and AuditPackage.
- `base44/functions/` — 32 backend functions (TypeScript `entry.ts`), including getWorkspaceTree, resolveWorkspaceAccess, migrateExistingWorkspaces, manageAssignment, transitionArticleStatus, generateAuditPackage.
- `base44/workflows/` — 8 workflow definitions (JSONC).
- `base44/connectors/` — 2 connectors (googledrive, one_drive).
- `base44/agents/` — 1 AI agent (framework_guide).
- `base44/shared/` — shared utils (automationSecret, escapeHtml, licenseGuard).
- `src/lib/rbac.js` — centralized RBAC: capability-based access control, route→capability mapping, nav group resolver.
- `src/lib/workspace.js` — frontend workspace utilities (tree fetch, access resolution, migration trigger).
- `src/lib/delegation.js` — frontend delegation utilities (UserCustomerAssignment CRUD, resolve user customers).
- `src/lib/tenantResolver.js` — pure tenant/context resolution (selected workspace → own tenant → live delegations), re-exported and wrapped as `useActiveCustomer()` by `src/lib/tenantContext.js`; the single place a page should read the active tenant from (FA2/FB3).
- `tools/validation-harness/` — the multi-identity validation harness (`npm run validate:harness`); see its own section below.

- **Escala de maturidade 0–5 por área (2026-09-29; verificada no preview).** `src/lib/validationReportModel.js` é o modelo único: `MATURITY_SCALE` (0 Inexistente … 5 Validado), `MATURITY_WEIGHTS` (crítica 2, alta 1,5, média 0,75, baixa/a verificar 0,25), `MATURITY_STATUS_FACTOR` (parcial 0,5; corrigido 0), `maturityForFindings()` e `buildMaturityMatrix()`. **O nível 5 significa «sem achados abertos» e é por isso que qualquer achado aberto tira pelo menos um nível** (arredondamento para cima a partir de 1) — sem essa regra, um achado de peso baixo não descia a nota e o rótulo contradizia a justificação (defeito real apanhado no preview e corrigido). A **mesma** função calcula as três famílias: as áreas do relatório, as áreas comerciais (`COMMERCIAL_AREAS`, FM1–FM6) e as categorias de requisitos NIS2 (`NIS2_AREAS`, medidas do art. 21.º/2 do RJCS) — ambas acrescentadas a `src/lib/platformAssessmentData.js`, cada uma apontando para os achados que a produzem. A nota aparece no cabeçalho de cada área (`MaturityBadge`) e na `MaturityMatrix` da página, sempre com a justificação; `buildReportModel()` devolve `area.maturity`. **Nunca escrever uma nota nem uma justificação à mão** — fechar um achado muda a nota, a justificação e a matriz no mesmo instante.
- **Documentação técnica derivada do repositório (2026-09-29; verificada no preview e no PDF).** `src/lib/repoInventory.js` lê `base44/**` no build com `import.meta.glob(..., { query: '?raw', eager: true })` e extrai o contrato de cada peça **do próprio código**: entidades → campos, obrigatórios e relações (campo `*_id`/`*_ids` cujo nome corresponde ao de uma entidade existente); funções → primeiro parágrafo do cabeçalho de documentação, ações do selector multiplexado (`action === "x"`), campos de entrada (desestruturação de `body`/`payload`/`data`) e chaves de saída (chaves de topo dos `Response.json({ … })`); workflows → gatilho, cron, eventos e `function_name` chamada; conectores e agente → tipo, scopes e `tool_configs`. `docsModel.js` combina isso com a narrativa curada (`DATA_MODEL_NOTES`, `SERVICE_MODEL`, `API_MODEL` e `FUNCTION_NOTES` — este **só** como recurso para as funções que não trazem cabeçalho) e **confronta o agrupamento editorial com o inventário**: uma entidade ou função que exista no repositório e não esteja em nenhum grupo de `DATA_MODEL` aparece como «sem grupo» na página e no PDF, e um item de grupo que já não exista aparece como «ausente do repositório». ## Validation harness (multi-identity)
`npm run validate:harness` (= `docker compose -f docker-compose.base44.yml exec -T web node tools/validation-harness/run.mjs`; add `--suite=api` or `--suite=ui`) runs the executable RBAC/tenant/licensing validation against the **local** backend and exits non-zero when a case fails. Its current state is 87 ok, 0 failures, 1 not verifiable locally (88 cases; 72 before the lifecycle/quota cases were added: `FM3.1`–`FM3.6` and `FM4.1`–`FM4.5`, which exercise renewal, the tier change with confirmed removals, the close with work to handle, the contractual quotas, the idempotent signal recording and the read-only change simulator (OP-M5); `FM1.1`–`FM1.3` and `FM2.1`–`FM2.7` before those exercise the offer/price lifecycle, the `change_action` history filter and the commercial registration in `provisionTenantLicense`).
- **Identity injection.** Each invocation carries the test identity in the `x-base44-dev-actor` header (base64 JSON), honoured by `base44/shared/devActor.ts` **only** when `BASE44_DEV_IDENTITY === "1"` — a variable set in `docker-compose.base44.yml` and nowhere else, so the path is off in every deployed environment. Never add it to another environment. Without the header a function behaves exactly as before, on the single authenticated session.
- **Prep order matters.** The api suite runs `seedLicenseData` first (the `LicenseModule` catalogue is what `provisionTenantLicense`'s `set_module` validates against, so without it the module-exception cases measure a missing catalogue) and `seedTestEnvironment` second (it is what enforces the declared test conditions: Delta without a subscription, the workspace↔customer link, completed assessments). **A third step — the commercial context — runs immediately after those two, before the first group:** the emulator survives between runs and the last commercial group leaves the verification tenant *closed* (`FM3.6`), so without restoring a live contract the earlier groups measure a closed client and fail with `module_not_licensed` (`DEL5`, `FA5.1`/`FA5.2` did exactly that). The offer and price in force are re-established separately, by that group's own prep, because `FM2.7` retires them on purpose.
- **A test case that writes idempotently must not use a fixed key.** `FM4.4` used a fixed period and only saw new rows on the first run; it now searches for a period that still returns new rows (months of a past century, from a random start) and asserts idempotency on that one. Same rule for anything seeded with a fixed identifier on this emulator: assume the state of the previous run is still there.
- **The ui suite loads the real decision code.** `src/lib/rbac.js`, `sidebarGroups.js`, `licenseModules.js` and `tenantResolver.js` are copied into a temp dir with their relative ESM imports given an extension, so the Sidebar/RouteGuard matrix and the tenant contract are exercised as shipped rather than re-implemented in the harness.
- **One case is not verifiable on the local emulator** and is reported as `n/a` (never as passing): `RLS1` — entity RLS is evaluated against the single authenticated session, and a tenant present only in `delegated_edit_customer_ids` is hidden on read. It needs a real backend. (`FB1.12` used to be the second one because the trail lived only in `AuditLog`, which that session cannot read; the licensing history is now its own entity read through `listLicenseChanges`, so `FB1.12`/`FB1.13` run for real.)
- The harness needs the local backend up (`base44 dev` inside the container) and the CLI token in the `base44-cli-auth` volume; it restarts nothing.

## Importação de bases de perguntas (rascunho → revisão → publicação)
O banco de perguntas ganhou entrada por ficheiro, sem perder a regra de que o browser nunca escreve no catálogo.
- **Entidades:** `QuestionImportBatch` (lifecycle `draft`/`published`/`discarded`/`reverted`, proveniência do ficheiro + contagens) e `QuestionImportItem` (uma linha por item — `framework`/`control`/`question` — com `state` `valid`/`warning`/`duplicate`/`error`/`applied`, `review_state`, `action`, `target_id`, `issues[]`, `similarity`/`similar_to`, o snapshot `before` e o `applied_id`). Nada é apagado pelo lote: `is_active: false` desativa.
